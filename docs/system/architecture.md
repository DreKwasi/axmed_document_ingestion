## Current state

The project is a single-repository FastAPI + Vue 3 document-intelligence system. The source PRD is [axmed_document_intelligence_prd.md](../product/axmed_document_intelligence_prd.md); the execution order is in [implementation-plan.md](../plans/implementation-plan.md). The backend map is [backend/app/README.md](../../backend/app/README.md): `api/` composes HTTP, `application/` contains use cases, `domain/` contains canonical interpretation and LangChain extraction (`app.domain.langchain_extractor`), `infrastructure/` contains persistence, `workers/` contains Huey execution, `security/` contains redaction, and `core/` contains configuration. Checked-in Alembic migrations persist batches, documents, quotations, source files under a generated local name, LiteParse representations, field evidence, fingerprinted mappings, review commands, correction evidence, review-learning jobs, email semantic-extraction jobs, processing events, model invocations, and evaluation runs in `backend/data/app.db`; Huey state lives separately in `backend/data/tasks.db`. Relative operational paths resolve from `backend/`, so API and Huey processes share the same database, queue, and source-upload directory regardless of their working directory. Multi-file batch upload creates a `batches` record and derives aggregate progress directly from independent child document jobs; unparseable files fail safely with an isolated failure reason without disrupting sibling documents. The architecture has two explicit intake paths: structured JSON uses deterministic schema recognition and trusted mapping memory; unstructured PDF, EML, and image inputs use format-specific parsing (LiteParse, MIME, and PaddleOCR) to retain source representation before PII-safe semantic extraction. All paths converge on `CanonicalQuotation`, then deterministic commercial validation/derivation, field confidence, provenance, and human review. For unstructured documents the LLM receives the generic parsed source context and is explicitly responsible for interpreting supplier quotation references, buyer RFQ references, supplier address country, named Incoterm place/country, and explicit product-origin statements; supplier-shaped regular expressions are not part of this semantic step. An Incoterm location is persisted as commercial context and never treated as evidence of product origin. Field confidence is an evidence-based `High`, `Medium`, or `Low` decision from source clarity, association certainty, independent validation, and conflicts; it is never an average or schema-completeness score. Missing values are commercial-availability exceptions, while derived values carry formula and validation status rather than extraction confidence. Every successful extraction becomes `pending_review`; only a human can move it to `approved` or `rejected`, and a correction is an auditable event that leaves it pending until that decision. Processing events are the browser/worker boundary and are replayed through reconnectable SSE. The Home source workspace consumes a source-level summary (availability, review status, product counts, issues, and notes) while the detail view reads normalized product data and field-level review evidence. GitHub Actions CI and automated PII audit checks enforce delivery hardening.

The PDF boundary deliberately retains LiteParse's raw page JSON and parsed page representation; the application does not build a universal table-reconstruction or Markdown conversion layer. LiteParse output is evidence for the semantic extractor, not a canonical quotation. The primary semantic call receives the layout-aware representation for table fidelity. A second, compact text-only LLM enrichment call receives the PDF reading order and the existing source keys, then fills only missing `Supply` and `Regulatory` fields. It cannot overwrite table-derived product, quantity, price, packaging, or commercial facts. Passing text from every page preserves scoped footnotes on table pages while avoiding the repeated layout geometry; it reliably applies semantic note scope (single item, list/range, exception, or remainder) to each line item.

Quotation snapshots remain in `quotations.payload_json` for immutable revision compatibility. The active line-item projection is normalized across `quotation_line_items` and child tables for INNs, strengths, price tiers, adjustments, and registered markets. Every non-null extracted leaf is also persisted in `quotation_field_values` with its value, raw source provenance, confidence category/reason, and human-review status; the API exposes these as `field_reviews`. `field_evidence` stores actual semantic source locations/excerpts and human corrections; a deterministic JSON mapping path is lineage and is not recorded there as source evidence. Derived normalized prices persist their formula, origin flag, and deterministic validation status, and expose no extraction-confidence band. `quotations.review_status` drives `GET /api/v1/review-queue`; `has_corrections` identifies an eventual approval with audited changes. `reviews.rejection_reason` retains the required structured reason. Alembic migrations `20260906_12` through `20260907_17` backfill and maintain these projections.

Worker progress is persisted before each meaningful semantic boundary and exposed through `GET /api/v1/documents/{id}/events` and the matching SSE stream. PDF and email extraction report preparation, semantic identification, normalization, completion, waiting, and failure; event serialization adds a user-safe `phase`, `message`, and redacted metadata. The Vue detail view replays these events as an extraction activity timeline, so reconnects do not lose the explanation of what the worker is doing. OCR/provider internals remain backend state and are not presented as a user-facing source status.
