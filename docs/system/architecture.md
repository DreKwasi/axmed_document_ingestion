## Current state

The project is a single-repository FastAPI + Vue 3 document-intelligence system. The source PRD is [axmed_document_intelligence_prd.md](../product/axmed_document_intelligence_prd.md); the execution order is in [implementation-plan.md](../plans/implementation-plan.md). The backend map is [backend/app/README.md](../../backend/app/README.md): `api.py` owns FastAPI setup and every public route; `documents.py` owns document and review operations; `extraction/` groups parsers, extraction pipelines, confidence, contracts, and normalization; `models.py` and `database.py` make persistence explicit; `events.py` owns processing activity; and `security/` owns redaction. There is no worker package or separate queue runtime. One `POST /api/v1/documents` request accepts one or many files, returns one array of document records, and isolates failures when several files are uploaded together. It does not create a separate batch record.

Confidence is exposed through two independent API summaries. `extraction_confidence` is a weighted source-recovery score built from source format, machine readability, parser quality, grounded evidence, and OCR quality. `mapping_confidence` is a canonical-field assignment score built from direct source paths, row/cell association, provenance, reconciliation, and conflicts. Every populated canonical field is assessed; a field without source-linked evidence is 0%/Low with a visible missing-evidence issue. The application handles those missing references with a bounded evidence request and requires an addressable PDF page, email body range, OCR page, or JSONPath reference. A source is `pre_approved` only when both scores are 100 and mapping has no issues; any other extracted candidate is `pending_review`. Low image quality remains visible as confidence evidence and never auto-rejects a candidate. `mapping_issues` is a deduplicated actionable list with an affected product-detail section; it replaces the synthetic review-issue count. The UI does not calculate or display a lowest-field confidence band.

Checked-in Alembic migrations persist documents, quotations, source files under generated local names, LiteParse representations, canonical field evidence, extracted source facts, review commands, processing events, model invocations, and developer evaluation runs in `backend/data/app.db`. Source files are not content-hashed or fingerprinted. JSON uploads use a bounded, iterative in-memory structural profile (depth-limited, path-budgeted, and array-sampled) and a per-document semantic extractor. The extractor returns source facts with raw values and JSONPaths; direct claims are value-checked against their pointers, then only certainly interpretable facts populate `CanonicalQuotation`. Unmapped facts are persisted, do not lower extraction confidence or create review issues, and are deliberately absent from the current product drawer. JSON profiles, recorded responses, fingerprints, mapping reuse, mapping confirmation, and correction learning are not stored. Unstructured PDF, EML, and image inputs use format-specific parsing (LiteParse, MIME, and PaddleOCR) before semantic extraction. OCR confidence and geometry remain in the redacted provider record for audit, while Gemini receives readable redacted OCR page text plus the original source media; no deterministic OCR row mapping sits between them. Sending original media is an explicit provider privacy boundary because pixel content cannot be text-redacted. All paths converge on deterministic commercial validation/derivation, field confidence, provenance, and human review. For unstructured documents the LLM receives parsed source context and is responsible for interpreting supplier quotation references, buyer RFQ references, supplier address country, named Incoterm place/country, and explicit product-origin statements; supplier-shaped regular expressions are not part of this semantic step. An Incoterm location is persisted as commercial context and never treated as evidence of product origin. Transit, shipping, or delivery duration is not assigned to product lead time unless the source explicitly identifies it as lead time. Full dosage-form phrases are retained and route is not modeled separately. Field confidence is an evidence-based `High`, `Medium`, or `Low` decision from source clarity, association certainty, independent validation, and conflicts; it is never an average or schema-completeness score. An extraction with at least one product becomes `pending_review`; a zero-product result becomes `failed`, with validated source facts retained as not reviewable. Only a human can move a reviewable source to `approved` or `rejected`, and a correction is an auditable event that leaves it pending until that decision. Processing events are replayed through reconnectable SSE. The Home source workspace consumes a source-level summary while the detail view reads normalized product data and canonical field evidence. GitHub Actions CI and automated PII audit checks enforce delivery hardening.

For image sources, OCR is a continuous source-quality signal, not a pre-extraction rejection gate. OCR-assisted and direct-vision extraction both run even when glare or poor legibility is detected; direct vision receives the original image when no trustworthy OCR region is available. Low OCR quality lowers extraction confidence but does not alter review eligibility. The two approaches remain peer attempts and neither can become canonical automatically. Home projects them as two source results. Mapping is assessed per result, while both share a source-condition extraction score.

The PDF boundary deliberately retains LiteParse's raw page JSON and parsed page representation; the application does not build a universal table-reconstruction or Markdown conversion layer. LiteParse output is evidence for the semantic pipeline, not a canonical quotation. The extraction call receives the layout-aware representation and complete reading-order context together, so table fidelity, notes, footnotes, and scoped narrative are handled in one extraction response.

Quotation snapshots remain in `quotations.payload_json` for immutable revision compatibility. The active line-item projection is normalized across `quotation_line_items` and child tables for INNs, strengths, price tiers, adjustments, and registered markets. Shipment HS customs codes remain document-level commercial terms; ATC codes and a separate product route are not modeled. Every normalized canonical leaf is persisted in `quotation_field_values` with its value, source provenance, confidence category/reason, and human-review status; the API exposes these as `field_reviews`. `field_evidence` stores actual semantic source locations/excerpts and human corrections only for canonical fields. `extracted_source_facts` stores all JSON facts, including unmapped ones, with their JSONPath and source-recovery confidence. Derived normalized prices persist their formula, origin flag, and deterministic validation status, and expose no extraction-confidence band. They are hidden from the overview table and rounded for display to no more decimal places than the quoted price. Deleting a source removes its exact stored upload and all document-scoped extraction, review, event, evidence, source-fact, and normalized projection records. `has_corrections` identifies an eventual approval with audited changes. `reviews.rejection_reason` retains the required structured reason. Alembic migration `20260907_19` replaces retired JSON mapping state with source-fact persistence; `20260907_20` removes redundant batch persistence; `20260907_21` marks existing unreviewed zero-product quotations as failed without changing completed human decisions.

Background-job progress is persisted before each meaningful semantic boundary and exposed through `GET /api/v1/documents/{id}/events` and the matching SSE stream. The API submits independent PDF, email, JSON, and OCR work to a bounded local executor (default four workers), so files from one upload do not wait on one another's model calls. Each job has its own SQLAlchemy session and reports preparation, semantic identification, normalization, completion, waiting, and failure; event serialization adds a user-safe `phase`, `message`, and redacted metadata. The Vue detail view replays these events as an extraction activity timeline, so reconnects do not lose the explanation of what the API is doing. OCR/provider internals remain backend state and are not presented as a user-facing source status.

## Application-orchestrated semantic extraction

The semantic path is an application-orchestrated pipeline inside API-owned background processing. It has three model-worker boundaries and a deterministic control boundary:

1. **Primary extraction**: deterministic source preparation creates an `EvidenceWorkspace` that preserves whole JSON/email sources and atomic PDF/OCR pages. A dedicated extraction-only response schema gives the model canonical values plus a reviewer narrative drawn from structured and narrative source content; the schema has no evidence fields.
2. **Extraction validation**: Python checks schema completeness and commercial rules only. It does not assess mapping confidence yet.
3. **Full grounding**: a second structured model call receives the complete canonical candidate, the exact populated fields requiring evidence, and the prepared source. It returns field-specific claims containing the canonical field, claimed source value, and addressable source reference. It cannot change extraction values.
4. **Grounding validation**: Python rejects claims for an unknown or unpopulated canonical field, a source reference that does not resolve, a claimed value that is not present at that reference, or a direct value that does not equal the extracted candidate. JSON claims additionally require a real JSONPath and the actual value at that path. Only accepted claims become persisted evidence or JSON source facts.
5. **Targeted evidence investigation**: while grounding leaves fields unsupported and the three-run limit has not been reached, application code makes an ordinary structured model request with the complete remaining ungrounded-field list, their extracted values, prior rejected claims, and the prepared source. It returns evidence claims only and cannot rewrite the candidate.
6. **Control and termination**: Python revalidates returned claims after every request and alone decides whether the loop repeats. A failed full-grounding request also enters this bounded loop. A response with no new claims stops immediately as no progress; otherwise the hard three-run limit applies. Fields still unresolved persist for warning/manual review.

`run_semantic_extraction` is the small public seam for this flow. It uses no LangChain agent, tools, middleware, or model-selected transitions. All model calls are selected and bounded by application code; tests simulate their structured responses without provider access. Google Gemini 3.5 Flash Lite is the sole code-owned provider.

The semantic component does not control media routing, commercial derivations, persistence, document status transitions, or approval. Format capabilities are supplied by the application: JSON paths and sibling context; PDF reading order, cells, pages, and regions; sanitized email chronology; and accepted OCR text plus masked image regions. Intermediate hypotheses never enter quotation state. Deterministic policy calculates extraction and mapping confidence from observable evidence and conflicts rather than accepting a model-authored confidence score. A primary-provider failure uses the configured fallback model; a repair failure leaves the last validated candidate intact with unresolved issues rather than crashing an otherwise usable extraction.

JSON, PDF, email, OCR-assisted image, and direct-vision image paths all use this orchestrated seam. JSON no longer performs a separate completeness-audit model call, PDF no longer performs a separate narrative-enrichment model call, and no path learns or reuses an approved supplier mapping.

The API terminal log is an operator-facing complement to those persisted events. One guarded `app`-namespace stderr handler receives API, parser, extraction, and event records after migrations finish their logging setup. Background tasks log scheduling, start, completion, and full failure boundaries with short record IDs. The semantic pipeline logs only safe operational metrics: source type, workspace mode/size, candidate extraction duration, line item counts, validation results, and exception class. Model source text, prompts, credentials, and raw provider responses are never logged.

The backend owns the user-facing CSV projection at `GET /api/v1/documents/export.csv`. It reads persisted document, quotation, source-fact, field-review, confidence, evidence, and image-attempt records and flattens terminal results into product rows; completed image attempts are independent source rows. Evidence canonical fields, source paths, source locations, methods, and superseded paths are exported with each applicable row. The frontend only initiates the file download and does not reconstruct export data.

## JSON structural profiling, bounded traversal, and scaling strategy

JSON uploads are profiled in-memory by [`profile_json`](file:///Users/andrewsboateng/Projects/axmed-takehome/backend/app/extraction/json.py) to build a structural inventory (`paths` and `candidate_collections`) that guides semantic extraction without persisting cross-document schemas. To ensure deterministic scaling on arbitrary, deeply nested, or large JSON inputs, the profiling engine operates under explicit runtime bounds:

1. **Iterative Traversal (Recursion Safety)**: Traversal uses an explicit DFS stack rather than Python call-stack recursion. Payloads exceeding Python's default stack recursion limit (e.g. > 1,000 levels deep) execute without `RecursionError`.
2. **Depth and Path Budgets**: Traversal enforces `max_depth` (default 20) and a hard path budget `max_paths` (default 500). Once the path limit is reached, traversal gracefully completes, preventing memory ballooning and upstream token saturation.
3. **Array Sampling and Wildcard Profiling**: In tabular/collection arrays (e.g., thousands of line items), inspecting every element yields redundant structural paths. The profiler samples up to `max_array_samples` (default 3) items to record leaf types and keys, captures full array `length`, notes `sampled_elements`, and exposes candidate uniform collections with wildcard notation (`$path[*]`).

### Massive JSON scaling and chunking architecture

For massive JSON documents (e.g. supplier catalogs or multi-thousand line quotations exceeding single-prompt context limits or memory thresholds):

- **Streaming Ingestion**: Instead of loading the entire JSON payload into an in-memory DOM, the ingestion tier uses event-driven streaming parsers (such as `ijson`) to detect document metadata and stream records from candidate collections directly from disk.
- **Header & Collection Partitioning**: Document-level context (supplier information, quote reference, currency, incoterms, payment terms) is profiled and extracted in an initial semantic pass. The primary line-item array is partitioned into bounded windows/chunks (e.g. 25–50 items per chunk).
- **Windowed Semantic Extraction**: Each line-item chunk is dispatched with the shared document-level context to the semantic model. Line items and unmapped source facts are extracted per chunk, validated against exact JSONPath locations, and verified deterministically.
- **Canonical Aggregation**: The line-item batches and source facts are merged into a single consolidated `CanonicalQuotation` and `DocumentRecord`, running commercial rules and validation across the unified result before human review.
